# bro2 v3.0 · 竞争顶级 Agent Harness 作战计划书

> 版本：v1.0（2026-11-08）· 基于 bro2 v2.2.2 实测现状
> 性质：**执行计划**，不是愿景文档。每条建议都绑定文件路径、命令与量化验收阈值。
> 配套：[BENCHMARK.md](../BENCHMARK.md)（可证伪定义）· [ROADMAP.md](../ROADMAP.md)（P0–P5）· [DELIVERABLES.md](../DELIVERABLES.md)（登记册）

## 0. 一页结论（TL;DR）

**诊断**：bro2 是一台**优秀的 harness 研究台**，还不是**有竞争力的 agent harness**。差距不在架构，在于**没有能测出 harness 价值的任务**——现有评测集是 19 个 4–5 步的脚本化短任务，真实强模型在上面只跑出 `avgSteps=2.67`，harness 的调度、压缩、纠错、工具设计几乎没有发挥空间。**用短任务测 harness，等于用直道测越野车。**

**战略**：不正面拼绝对任务分数（拼不过模型厂商的独家模型 + 团队 + 算力），改打**唯一能赢且可证伪的赛道**——

> **同模型增益**：固定同一个模型，只换 harness，bro2 能提升多少？
> **成本前沿**：用便宜/免费模型 + harness，能否达到贵模型裸跑的水平？

这两条赛道竞品结构性缺席：Claude Code 绑 Claude、Codex 绑 GPT，没有人系统性优化"任意模型 × 可插拔 harness"。bro2 的模型无关架构、`KeylessAggregator`、`HybridProvider`、可审计 RSI 正好是为此而生。

**路径**：五个战役，13 周。地基是 W1（重建基准），主引擎是 W2（编码 ACI），W3/W4 把两大设计目标从"演示"变"实测"，W5 才谈分发。

**90 天唯一硬指标**：在自建真实任务集上，`HLR（Harness Lift Ratio）≥ 0.30`，且 `8B 级本地模型 + bro2 ≥ 70B 级裸跑得分的 90%`。达不到就诚实降级定位（见 §8.4）。

### 1.3 五个结构性缺口（按致命程度排序）

| # | 缺口 | 事实 | 后果 |
| --- | --- | --- | --- |
| 1 | **任务集太浅** | 19 个任务，`maxSteps` 2–10，绝大多数 4–5；都是单文件、短链路 | 测不出 harness 差异；任何"改进"都可能是在拟合噪声 |
| 2 | **无代码感知 ACI** | 只有 `file_read/write/edit/list/delete/search_files`（纯文本替换）+ `shell` | 真实编码任务编辑成功率低、重试多、token 浪费 |
| 3 | **沙箱非 OS 级** | 应用层路径白名单，非容器/seccomp | 无法安全跑不可信任务、无法进生产 |
| 4 | **自进化表达力窄** | `evolve` 只能在 5 个 policy 维度上搜索 | 只能调参，改不了提示、工具描述、上下文策略 |
| 5 | **无外部对照** | 从未与同期 harness 同模型同任务对照 | `verdict=not-proven` 无法推进，也不知道自己真实排位 |

## 2. 竞争格局拆解

> 以下为**公开产品能力的结构性观察**（架构路线、绑定关系、生态形态），**不是实测分数**。
> 本项目的红线是不引用未经自己复现的性能数字；W1 战役要求自行实测对照（见 §4.1）。

### 2.1 顶级 harness 的三条路线

| 路线 | 代表 | 结构性优势 | 结构性约束 |
| --- | --- | --- | --- |
| **模型厂商绑定型** | Claude Code、Codex CLI、Gemini CLI | 与自家模型深度协同；终端体验打磨到极致；分发即装机量 | 只对自家模型最优；内层 harness 不开放；跨模型迁移无动力 |
| **开源框架/应用型** | OpenHands、SWE-agent、Aider、Cline | 社区与插件生态；公开榜单持续提交；真实任务经验厚 | 工程质量参差；自进化缺失；多为"应用"而非"内核" |
| **商业端到端型** | Devin、Factory、Amp | 交付结果而非工具；企业采购路径清晰 | 黑盒、贵、不可审计；无法嵌入他人产品 |

bro2 的坐标：**第 2 类的最底层**——它是内核，不是应用。这既是劣势（没有开箱即用的任务能力），也是唯一可能的优势（可以被别人装配）。

### 2.2 九维差距矩阵

评级：◎ 领先 · ○ 持平 · △ 落后 · ✗ 结构性缺失

| 维度 | 厂商绑定型 | 开源应用型 | **bro2** | 说明 |
| --- | --- | --- | --- | --- |
| 真实任务能力（长程/多文件） | ◎ | ◎ | **✗** | 无长程任务集，`avgSteps=2.67` |
| 编码专用 ACI（编辑/诊断/repo map） | ◎ | ◎ | **△** | 只有字符串替换 + shell |
| 上下文工程（压缩/检索/记忆） | ◎ | ○ | **○** | 有 budget/compact/retrieval，但无 repo map |
| 模型无关性 | ✗ | ○ | **◎** | 11 provider + 聚合 + 协同，架构级领先 |
| 成本控制（缓存/本地承接/免费端点） | ✗ | △ | **◎** | `Hybrid` + `Keyless` + 学习型路由，竞品几乎没有 |
| 可观测与可审计 | ○ | △ | **◎** | Trajectory 唯一真相源 + 结构化事件 |
| 自进化（可验证） | ✗ | ✗ | **◎** | 唯一有冻结尺子 + 只增账本 + 防 reward hacking 的 |
| 沙箱与安全 | ◎ | ○ | **△** | 应用层白名单，非 OS 级 |
| 生态与分发（MCP/IDE/社区） | ◎ | ◎ | **✗** | 无 IDE 集成、无社区、无榜单 |

**读法**：bro2 在两个维度（模型无关、自进化）结构性领先，两个维度（成本、可观测）有明显优势，但在**决定用户是否使用**的三个维度（任务能力、ACI、生态）上全面落后。

这决定了战略：**不能从落后维度发起正面进攻，必须把领先维度转化成可被感知的价值**。

### 2.3 为什么正面战场必败

1. **模型访问不对等**：厂商型 harness 能用未公开的模型版本与专属推理参数，第三方永远慢一拍。
2. **数据飞轮不对等**：开源应用型的真实任务轨迹是百万级，bro2 是 19 个脚本任务。
3. **人力不对等**：单人 + AI 辅助，无法同时做内核、应用、IDE、生态。

### 2.4 三个可赢的机会窗口

| 窗口 | 逻辑 | 竞品为何不做 |
| --- | --- | --- |
| **同模型增益（Harness Lift）** | 固定模型只换 harness，量化每一处 harness 设计的边际贡献 | 厂商没有动机证明"换 harness 也能提升"，那会削弱模型叙事 |
| **低成本可用性（Cost Frontier）** | 小模型/免费模型 + 强 harness，逼近大模型裸跑 | 厂商的收入模型要求你买更大模型 |
| **可审计自进化（Verifiable RSI）** | 每轮改进有账本、有冻结尺子、可回放、可证伪 | 黑盒产品无法提供，学术项目工程化不足 |

**这三个窗口共用同一个前提**：必须有一套能测出差异的基准。这就是 W1 必须先做的原因。

## 3. 战略：把"架构优势"翻译成"可测增益"

### 3.1 北极星指标

**HLR — Harness Lift Ratio（同模型增益比）**

```
HLR = (Score(bro2 + Model M) − Score(MinimalHarness + Model M)) / Score(MinimalHarness + Model M)
```

- `MinimalHarness`：只保留「单轮 LLM 调用 + 工具调用解析 + 结果回喂」的最小循环（约 150 行，可另建 `baseline/minimal-harness.ts` 作为对照组）。
- 分母用最小 harness 而非裸模型，因为裸模型无法完成工具任务，会除零。
- **这个指标的好处**：它把"bro2 好不好"变成"bro2 相对于一个诚实基线好多少"，不可被模型升级掩盖，也不可自评。

**CAS — Cost-Adjusted Score（成本校正得分）**

```
CAS = Score / (TotalTokens × UnitPrice + WallClockSeconds × 0.001)
```

用于回答"同样的钱，谁办成的事多"。

### 3.2 三个不可让步的护栏

1. **不伪造**：所有对外数字必须来自 `data/**` 可复现报告；`verdict` 保持 `not-proven` 直到第三方复现。
2. **不回归**：任何 W2–W4 的改动都必须过 `npm test` 全绿 + L1 确定性集不退化（overall 保持 1.0）。
3. **不自评**：候选方案的自报收益不参与晋升判定（沿用 `live-contrast` 的既有约束）。

### 3.3 定位话术（用于 README / 发布）

> bro2 不争"最强 agent"，它回答一个别人不回答的问题：**同一个模型，harness 能让它强多少？**
> 附一份可复现的账本：每个 harness 改动的边际贡献、每次改进的探测成本、每个模型的成本-能力坐标。

### 3.4 工程宪法：代码要少，质量要高

**这是约束条件，不是口号。** Agent harness 的复杂度会自我膨胀——每加一个能力就多一层分支、多一个配置、多一处 fail-open。bro2 的竞争力恰恰建立在"可读、可审计、零依赖"上，所以把"少而精"写成可执行的门禁。

**当前基线（v2.2.2，作为预算起点）**

| 指标 | 现状 | 硬上限 | 说明 |
| --- | --- | --- | --- |
| 源文件数 | 72（`src` + `bin` + `scripts`） | 90 | 超限必须先合并或删除；新增文件须说明为何不能并入现有模块 |
| 源代码行 | 13,288 | 16,500 | 五战役合计预算 3,000 行，超出即阻断 |
| 单文件行数 | 最大 661（`observability/eval.ts`） | **700** | 软目标 400；超 400 需在文件头写清职责边界 |
| 测试代码行 | 2,791 | — | 测试/源 ≥ **0.15**（当前 0.21） |
| 运行时第三方依赖 | **0** | **0** | 硬约束，任何 PR 引入即拒 |
| 平均文件行数 | 72 | 120 | 超过说明职责没拆干净 |

**五条工程纪律**

1. **删除优先于新增**：每个版本至少净删 1 处死代码 / 重复逻辑。删不掉的部分，说明设计有问题。
2. **一个模块必须能回答"删掉它损失什么"**。答不出来就是过度设计，不合并。
3. **不引入抽象直到有第三个用例**。两个相似实现允许重复，第三次出现才提取——避免过早抽象带来的间接层。
4. **新增能力必须带"能失败"的测试**。测试先红后绿；没有失败路径的测试不算测试。
5. **配置项是负债**。每加一个开关，就要回答"默认值错了谁会受伤"。能用约定替代的，不加配置。

**LOC 预算按战役分配（超出即停手重设计，不是加班补）**

| 战役 | 新增源行预算 | 新增测试行预算 | 说明 |
| --- | --- | --- | --- |
| W1 基准重建 | ≤ 700 | ≤ 350 | 任务集是数据，不算代码 |
| W2 编码 ACI | ≤ 900 | ≤ 450 | repomap + apply_patch + 降级链 |
| W3 容错矩阵 | ≤ 350 | ≤ 150 | 主要是脚本编排，不是框架 |
| W4 自进化可信化 | ≤ 600 | ≤ 300 | 算子扩展 + OOD + 晋升判据 |
| W5 产品化外证 | ≤ 450 | ≤ 150 | SDK 薄封装 + 容器 + 文档 |

**门禁化**：`npm run budget:check` 作为第 13 道阻断门禁，超限即失败。阈值集中在 `data/plan/budget.json`，调整需在 `BENCH-v2.md` 记录理由——防止"为了让门禁变绿而调阈值"。

## 4. 五大战役

> 每个战役格式：现状 → 目标 → 交付物（文件级）→ 验收（量化）→ 工期 → 依赖 → 风险。

### W1 · 基准重建：让 harness 有地方使劲

**现状**：19 个任务、4–5 步、单文件、脚本化。`avgSteps=2.67` 意味着模型平均 2.67 步就结束，压缩、纠错、重规划这些 harness 核心机制根本没被触发。

**目标**：建立三层任务集，让"harness 差异"能被测出来。

> **进度**：`W1-01` ✅（v2.3.1）任务集可装载、可校验、可复跑，l1 指纹与既有评测一致（`d1419b1efaa7`）；
> `W1-02` ✅（v2.3.2）3 个 fixture 仓库快照已就位（各埋 1 个真缺陷，可见测试 16 项全绿，内容指纹钉住）；
> `W1-04` ✅（v2.4.0）隐藏测试执行器 + 双态校准：任务在原始快照上必失败、应用参考解后必通过，18/18 成立；
> `W1-03` ✅（v2.4.0）首批 18 个 L2 真实工程任务（3 仓库 × 6），全部绑定 `repo` + `hiddenTests`，`liveOnly` 不掺确定性分。
> `W1-05` ✅（v2.5.0）双跑校准：kilo/standard 17/18 vs kilo/minimal 17/18，**差距 0pp**——负结果；
> `W1-07` ◐（v2.6.0）L3 首个任务（`ts-todo`，三文件 + 过时断言）1/1，standard 12 步 vs minimal 10 步，**仍 0pp**。
> **关键发现**：`minimal` 带 `shell`，在单仓库无故障场景下会被抹平差异；继续堆同质任务只会得到更多 0pp。
> 故障注入（v2.7.0）✅：第一个能放大差异的场景——429/500 注入下重试开 3/3 vs 关 0/2；参数名拼写下 repair 3步/0错误 vs fail 8步/1错误。
> 首个正向 harness 增益证据，边界见 `docs/BENCH-v2.md` §5.3（不改变无故障 0pp 结论）。
> 脏故障与扩容（v2.8.0）✅：timeout / retry-after / empty-response 三类真实形态 + 空响应守卫；
> 故障任务 3 → 9 个。三组 on/off：路由重试 5/5 vs 0/5、空响应守卫 2/2 vs 0/2、repair 效率级。
> **弱模型对照（候选 2）为负结果**：4 个免 Key 端点全部链路故障 / 抖动，拿不到可信弱模型，
> 证据缺口如实保留（见 `docs/BENCH-v2.md` §5.4）。补齐条件：链路稳定且明显弱于 kilo 的真实端点。
> 确定性回归（v2.9.0）✅：`faults.provider` 在 deterministic / live 均生效，三组 on/off 对照
> 从「只能靠 kilo 人工跑分」升级为**离线可复算的第 18 道发布阻断门禁**（`npm run fault:check`，
> 3/3 接受）；零新增源文件、未上调代码预算阈值。边界见 `docs/BENCH-v2.md` §5.5。
> **W1-06 暂缓**：账本里它是下一个任务卡，但「L2 扩到 60 个同质任务」已被 0pp 负结果否定；
> 继续堆同质任务只会得到更多 0pp，先补齐可放大差异的场景与确定性回归底座再扩容。

| 层 | 用途 | 规模 | 判定方式 |
| --- | --- | --- | --- |
| **L1 回归层** | 现有 19 任务，守协议与治理不回归 | 19（保留） | 脚本化，overall 必须 1.0 |
| **L2 真实工程层** | 多文件仓库的 bug fix / feature / refactor | **≥ 60** | **隐藏测试 + 无回归 + patch 可应用** |
| **L3 长程压力层** | 20–40 步、需中途纠错与上下文压缩 | **≥ 12** | 隐藏测试 + 步骤预算内完成 |

### W2 · 编码 ACI：lift 的主引擎

**现状**：`file_edit` 是"精确匹配替换第一次出现"，无定位容错、无 diff 语义、无诊断回环。真实编码任务里这是最大的失败源。

**目标**：把通用文件工具升级为**代码感知的 Agent-Computer Interface**，直接提升编辑成功率与 token 效率。

> **进度（v2.5.0）**：`W2-01` repomap ✅（预算受限的符号索引，入度排序）；`W2-02` apply_patch ✅（多文件/多块、行号漂移可定位、失败零写入）；
> `W2-03` diagnostics ✅（node:test / unittest / tsc 三类输出结构化）；`W2-04` 编辑降级链 ✅（精确 → 空白归一化 → 去缩进，**只在唯一命中时降级**）；
> `W2-05` aci:check ✅（策略级 7/7：改对、该拒就拒、零半成品）。**尚未证明**这些改进提升了 L2 通过率——需要同模型 A/B，属 W2-06。

**交付物**

| 文件 | 内容 | 关键设计 |
| --- | --- | --- |
| `src/context/repomap.ts` | 符号索引（文件 → 类/函数/导出/导入关系） | 零依赖：正则 + 缩进启发式；输出**预算受限**的树状摘要（默认 ≤ 1200 tokens），不是全量 dump |
| `src/tools/builtins/code.ts` | `apply_patch`（unified diff，支持多处）、`search_symbol`、`diagnostics`（跑 tsc/eslint/pytest 并结构化） | patch 失败时返回**可操作的定位提示**（最近匹配行号 + 上下文），而不是 "failed" |
| `src/tools/repair.ts`（扩展） | 编辑失败自动重试策略：精确匹配 → 空白归一化 → 块级定位 → 请求重读片段 | 每次降级都记入 trajectory，便于事后归因 |
| `src/cognition/aci.ts` | ACI 策略：工具返回的截断/摘要/优先级规则 | 统一"信息密度"口径，避免工具 dump 淹没上下文 |
| `tests/aci.test.ts` | 编辑成功率、降级链路、repomap 预算 | 断言绑定真实分支 |

**验收**

| 指标 | 基线（v2.2.2） | 目标 |
| --- | --- | --- |
| 编辑一次成功率（L2 任务） | 需实测 | **≥ 75%** |
| 平均每任务编辑尝试次数 | 需实测 | **下降 ≥ 30%** |
| 每任务平均 token | 需实测 | **下降 ≥ 20%** |
| L2 通过率 | 需实测 | **+15pp** |
| L1 回归 | 1.0 | 保持 1.0 |

> 基线必须先用 W1 的 `bench:v2` 测出来再填，**不允许估算**。这是本计划的第一条纪律。

**LOC 预算**：源 ≤ 900 / 测试 ≤ 450（`repomap` + `code.ts` + 降级链，三处都要控）
**工期**：4 周（第 4–7 周，与 W1 尾部交叉）
**依赖**：W1（没有 L2 任务就无法验证）
**风险与缓解**

| 风险 | 缓解 |
| --- | --- |
| 零依赖约束下 repomap 质量差 | 先做"够用版"：只索引导出符号与 import 边；用 L2 实测决定是否值得引入 tree-sitter（若引入，作为**可选 devDependency**，不破坏零依赖运行时） |
| `apply_patch` 与现有 `file_edit` 并存导致模型选错 | 工具描述里写清适用场景；`diagnostics` 在 patch 失败后主动建议下一步 |

### W3 · 容错矩阵：把"目标 2"从演示变实测

**现状**：`hybrid:demo` 显示 `remoteCallRatio 100%→14.3%`，但这是**脚本化模拟**；真实模型下"小模型 + harness 能否顶住"从未测过。且 550B 实测里 `robustness=0`，说明容错链路在真实任务上没生效或没被验证。

**目标**：产出**成本-能力前沿曲线**，用数据回答"便宜模型能不能用"。

**交付物**

| 文件 | 内容 |
| --- | --- |
| `scripts/model-matrix.ts` | 模型阶梯 × harness 配置的矩阵跑分器 |
| `data/matrix/<ts>.json` | 每格：`score / tokens / latency / remoteCallRatio / errors` |
| `docs/COST-FRONTIER.md` | 自动生成的报告：曲线 + 拐点分析 + 推荐配置 |
| `src/models/route-experience.ts`（扩展） | 路由经验回写增加"任务类型"维度，而非只看请求结构 |

**矩阵设计**

| 维度 | 取值 |
| --- | --- |
| 模型阶梯 | 本地 0.5B / 3B / 8B · 免费 20B / 70B / 550B（约 6 档） |
| harness 配置 | 最小 harness · bro2 默认 · bro2 + hybrid · bro2 + hybrid + 学习型路由（4 档） |
| 任务 | L2 抽样 20 个（控制成本） |
| 重复 | 3 次，温度 0，固定 seed（端点支持时） |

**验收**

- 矩阵跑通，产出 6×4×20×3 的完整结果，缺失格必须显式标注 `unavailable` 而非 0。
- **核心结论门槛**：`8B + bro2 ≥ 70B + 最小 harness 的 90%`；若达不到，如实报告实际比例。
- 远程调用占比与得分的散点图显示**帕累托前沿**至少 2 个非支配点。

**LOC 预算**：源 ≤ 350 / 测试 ≤ 150（编排脚本，不是框架）
**工期**：2 周（第 7–9 周）
**依赖**：W1（任务）、W2（否则小模型编辑成功率过低，结论会被 ACI 缺陷污染）
**成本估算**：20 任务 × 3 重复 × 6 模型 ≈ 360 次运行，按每次 30k tokens ≈ **10.8M tokens**；免费层可覆盖大部分，付费兜底预算 **$30–80**。
**风险与缓解**

| 风险 | 缓解 |
| --- | --- |
| 免费端点限流导致矩阵缺格 | 每格重试 2 次 + 记录 `unavailable`；用 `KeylessAggregator` 自动转移 |
| 小模型 tool_calls 不支持 | 先跑 `doctor` 能力探针，不支持的原生工具调用的模型改走 `text-json` 解析分支并单独标注 |

**现状**：`evolve` 只在 5 个 policy 维度搜索（loopDetection / grounding / parallel 等），表达力窄；水位账本的 14 轮全部来自**同类失败模式**（`F:tool-error|low|tooled`），跨类泛化未验证。

**验收**

| H1 | 为了让数字好看而调任务难度 | 任务难度一旦校准即冻结；变更需在 `BENCH-v2.md` 记 changelog 并重跑历史基线 |
| H2 | 用 holdout 调参 | holdout 只在发布前跑一次；跑的次数记入账本 |
| H3 | 把 harness 增益说成模型能力 | README 与报告统一措辞："harness 贡献，非模型能力" |

### 8.4 退出条件（诚实降级）

若 W1 + W2 完成后（第 7 周）出现以下任一情况，**停止扩张，改写定位**：

1. **HLR < 0.10**：说明 harness 在当前任务上贡献极小 → 转向"可审计 / 可嵌入内核"单点定位，放弃"增益"叙事。
2. **L2 通过率提升 < 5pp 且 token 不降**：ACI 改造无效 → 回滚 W2，把资源转 W3 成本赛道。
3. **免费端点无法支撑 3 次重复**：矩阵不可信 → 缩小到 2 档模型 × 2 档 harness，只做定性结论。

> 降级不是失败，是**可证伪性的兑现**。这正是 bro2 相对竞品的核心差异。

## 11. 自治执行机制：不靠提醒，靠外置状态机

> 前面十节回答"做什么"。这一节回答"怎么让它自己往前走，而不是每次等人提要求"。

### 11.1 问题的本质

持续改进断掉的真实原因不是能力不足，是**状态留在了对话里**：上一轮做到哪、为什么卡住、哪个坑踩过——全在上下文里，一旦会话结束就归零，下次只能重问一遍。

所以解法不是"更努力"，而是**把状态外置到仓库**：进度、教训、阻塞项全部落成只增账本，任何一次会话（人或 agent）读一遍就能接上。

### 11.2 三本账

| 文件 | 性质 | 内容 | 谁写 |
| --- | --- | --- | --- |
| `data/plan/backlog.jsonl` | 只增定义 | 每个任务：`id / battle / title / accept / loc / deps` | 人（规划时） |
| `data/plan/journal.jsonl` | 只增事件 | 每次尝试：`start / done / fail / block` + 证据 + 实际 LOC | 执行器（每轮） |
| `data/plan/lessons.jsonl` | 只增教训 | 可复用的工程教训：`trigger / action / evidence / confidence` | 执行器（失败或反直觉成功时） |

**状态不单独存**：当前进度由 `journal` 折叠得出（`todo / doing / done / blocked`），与 `Trajectory` 是唯一真相源同一哲学。不存在"状态文件和实际不一致"的可能。

### 11.3 每轮的标准动作（tick 协议）

```
1. next    读 backlog + journal 折叠 → 选下一个 ready 任务（deps 全 done）
           同时检索 lessons，命中则打印「已知坑」
2. 执行    在 LOC 预算内实现，先写会失败的测试
3. 验证    npm test + project:status（含 budget:check）
4. 记账    done  → journal{event:done, evidence:<sha>, loc:<n>}
           fail  → journal{event:fail, reason} + lessons{trigger, action}
5. 发布    npm run ship（提交 + 推送 + 自检）
6. 交接    下一轮从第 1 步重来，状态全部来自账本，不依赖对话记忆
```

一条命令查看当前该做什么：

```bash
npm run auto:next      # 下一个任务卡（含验收标准、LOC 预算、命中的历史教训）
npm run auto:status    # 五个战役的 done/total、阻塞项、最近 5 条 journal
```

### 11.4 三阶段自治：先说清哪一步还不能交给它

诚实地说，**现在还不能无人值守**。分三步走，每步的边界写死：

| 阶段 | 时间 | 谁执行 | 谁决策 | bro2 的角色 | 退出条件 |
| --- | --- | --- | --- | --- | --- |
| **A · 参谋** | 现在 – W2 完成 | 外部 agent（我） | 人定方向，agent 排期 | 提供账本、门禁、教训检索 | W2 交付，`apply_patch` + `diagnostics` 可用 |
| **B · 半自动** | W2 – W4 | bro2 自己跑机械任务（补测试、修 lint、改文档、加任务集条目） | agent 审阅 + 人抽检 | 读 backlog → 改代码 → 跑门禁 → 记账 | 连续 10 个机械任务一次通过率 ≥ 70% |
| **C · 自提议** | W4 之后 | bro2 提编辑 + 自评测 + 自记账 | 人只批红线（治理/预算/对外声明） | 自己 propose → probe → 晋升 | OOD 不退化且连续 20 轮无治理违规 |

**阶段 B 的启动条件必须先用数据满足**，不能拍脑袋提前：
- `npm run bench:v2 -- --layer l2` 上，bro2 自主完成的机械任务一次通过率 ≥ 70%；
- 编辑降级链（W2）一次成功率 ≥ 75%；
- 单任务 LOC 超预算率 < 10%。

**阶段 C 的前置**：W4 的 `promote.ts` 必须能在 OOD 退化时**自动阻断**，且阻断记录可在 `journal` 里复核。做不到就停在 B。

### 11.5 教训怎么变成"bro2 自己掌握"

不是写进提示词让它"记住"，而是**每次选任务时强制检索、每次失败时强制写入**：

```jsonc
// data/plan/lessons.jsonl
{"at":"2026-11-09T10:12:00Z","scope":"engineering",
 "trigger":"给 file_edit 增加降级链",
 "action":"空白归一化会误改缩进；先备份原始缩进，再归一化匹配，最后按原缩进回填",
 "evidence":"journal:W2-03","confidence":2}
```

- `trigger` 用**任务标题 + 涉及文件**做关键词匹配（与 `ExperienceBank` 的指纹检索同一思路，但作用域是工程决策而非 harness 编辑）。
- `confidence` 每次被复用且成功 +1，失败 −1；降到 0 自动失效（不删除，保留审计）。
- `auto:next` 会把命中的教训**打印在任务卡上**，执行者无法绕过——这是"掌握"的最小可验证形式：**教训命中率**与**复用后失败率**都可从账本算出。

> 这一层故意不复用 `src/rsi/experience.ts`：那边的指纹是「失败模式 × harness 编辑」，这边的指纹是「工程任务 × 文件」，语义不同。**两个用例不抽象**，等 W4 出现第三个再合并（§3.4 纪律 3）。

### 11.6 必须停下来问人的四条红线

自治不等于失控。以下情况执行器**必须停止并上报**，不得自行决定：

1. **改判定口径**：任务通过标准、证据阶梯、`verdict` 语义。
2. **动预算阈值**：`data/plan/budget.json` 的任何上调。
3. **引入运行时依赖**，或改变零依赖承诺。
4. **对外声明**：README/发布文案里任何"领先/最强/超过"类表述。

其余（实现方式、文件拆分、测试策略、任务顺序）由执行器自行决定，并在 `journal` 留痕。
